# MetaNode 永续合约拆解学习笔记

> 范围：只用学 **智能合约**。前端、后端不在本笔记里。  
> 代码目录：`perpetual-contract/src/`  
> 用法：按课时走。每课先打开文件，再问「谁能调、改的是 paper/credit 还是保证金、会不会把账户打成不安全」。过关再进下一课。

---

## 怎么用

1. 左右开：笔记 + 对应 `.sol`。
2. 贯穿数字（建议抄在纸上）：

```
市场：BTC-PERP
Alice 做多 1 BTC @ 30000 USDC
  paper  = +1e18
  credit = -30000e6     （USDC 6 位）

Bob 做空 1 BTC @ 30000
  paper  = -1e18
  credit = +30000e6

标记价 markPrice 后涨到 31000
初始保证金率 IMR = 10%（10 倍杠杆）
维持保证金率 MM  = 5%
资金费累计值 fundingRate 从 0 变成 +1e14（仅作符号示例）
```

3. 学习以 `src/` 为准。`test/` 用来对照场景，不是实现。

## 第 0 课：先搞懂产品（不看代码）

**目标：** 能讲清永续和现货、和到期期货差在哪。用时约 20 分钟。

现货：买真正的 BTC。  
到期期货：到期交割。  
永续：没有到期日，用**资金费**让合约价跟着现货走。

做多：赌涨。价格涨，仓位价值变正。  
做空：赌跌。价格跌，仓位价值变正。

三个必须先接受的设计：

1. **订单不在链上。** 链上只结算已经配对好的结果。
2. **仓位不是「方向枚举 + 均价」两列。** 只用 paper 和 credit，现价来了再算盈亏。
3. **保证金在 Dealer，仓位在 Perpetual。** 一个 Dealer 可以挂 BTC、ETH 两个市场，全仓共享 USDC。

**过关：** 用户签完单但 Relayer 不上链，仓位变了吗？Alice 只 deposit 没成交，Perpetual.balanceOf 是多少？

## 第 1 课：类型 —— Types.sol

**目标：** 能默写 Order 五个字段和 RiskParams 里四个比率。用时约 30 分钟。

打开 `libraries/Types.sol`。

### 1.1 Order

- `perp`：哪个市场
- `signer`：谁的仓位会被改（通常是用户地址）
- `paperAmount`：正做多，负做空
- `creditAmount`：必须和 paper **异号**
- `info`：四个数打进一个 bytes32：makerFee、takerFee、expiration、nonce

价格不单独存：`price ≈ |creditAmount| / |paperAmount|`。

贯穿例子 Alice 买单：`paperAmount = +1e18`，`creditAmount = -30000e6`。

### 1.2 RiskParams

- `initialMarginRatio`：开仓/取款要用，10% → 最高约 10x
- `liquidationThreshold`：低于这个净值/敞口比就可以清算
- `liquidationPriceOff`：清算折扣
- `insuranceFeeRate`：清算时抽去保险账户
- `markPriceSource`：标记价合约
- `isRegistered`：没注册不能交易

### 1.3 State 里先盯这几张表

- `primaryCredit[user]`：USDC 保证金（可负，表示亏穿待坏账）
- `openPositions[user]`：该用户开着仓的 Perp 列表
- `orderFilledPaperAmount[orderHash]`：这张单已经成交多少
- `validOrderSender[relayer]`：谁能提交 trade
- `fundingRateKeeper`、`insurance`

**过关：** 订单里没有 `price` 字段，成交价从哪来？Maker 的 `credit/paper`。

## 第 2 课：Perpetual 账本 —— 最核心的一课

**目标：** 手算 `balanceOf`，并说清为什么资金费不用 for 循环。用时约 45 分钟。

打开 `Perpetual.sol` 从头读到 `balanceOf`、`updateFundingRate`，先不要看 `trade`。

存储：

```
struct balance { int128 paper; int128 reducedCredit; }
mapping(address => balance) balanceMap;
int256 fundingRate;   // 累计值
```

公式（写在纸上，后面每课都用）：

```
credit = paper × fundingRate + reducedCredit
```

刚开仓、fundingRate=0 时，reducedCredit 就是 credit，即 -30000e6。

Keeper 把 fundingRate 从 0 改成 Δ：

```
Alice paper=+1  → credit 增加  1×Δ   （多头收钱，若 Δ>0）
Bob   paper=-1  → credit 减少 |1×Δ| （空头付钱）
```

**没有人改 Alice 的 mapping。** 这就是 reducedCredit 存在的唯一理由。

`updateFundingRate` 仅 `onlyOwner`，owner 是 Dealer。

**过关：** fundingRate 从 0 升到 0.01（假设已对齐精度），Alice 的 `balanceOf` 里 credit 如何变？存储里的 `reducedCredit` 变了吗？（应变 credit，不应变 reducedCredit。）

## 第 3 课：结算 _settle

**目标：** 开仓、加仓、平仓时 storage 怎么改。用时约 35 分钟。

打开 `Perpetual._settle`。

步骤：

1. 读旧 paper、旧 reducedCredit，加上 `creditChange` 得到新 credit（已含当前 fundingRate）
2. `newPaper = oldPaper + paperChange`
3. `newReducedCredit = 新 credit - newPaper × fundingRate`
4. 写回
5. 若旧 paper==0：通知 `Dealer.openPosition`（登记这个市场）
6. 若新 paper==0：把剩余 reducedCredit 当已实现盈亏 `realizePnl` 打进 `primaryCredit`，再清零

贯穿例子：Alice 平掉 1 BTC，假设标记价 31000，成交 creditChange 大约 +31000e6（忽略手续费）：

```
旧 paper=+1, 旧 credit≈-30000
新 paper=0
剩余 credit ≈ +1000  → realizePnl(+1000) 进入 Dealer.primaryCredit
```

**过关：** 为什么平仓要把 PnL 挪到 Dealer，而不是留在 Perpetual？因为 paper=0 以后 `paper×fundingRate` 不再贡献，剩下的就是已经实现的美元，应回到保证金账户，给别的市场用（全仓）。

## 第 4 课：trade 与 approveTrade

**目标：** 画出「Relayer → Perp → Dealer → 再回 Perp」的圆。用时约 40 分钟。

### 4.1 `Perpetual.trade`

```
(traderList, paperChange, creditChange) = Dealer.approveTrade(msg.sender, tradeData)
对每个人 _settle
require Dealer.isAllSafe(traderList)
```

`msg.sender` 是 orderSender（Relayer），不是 Alice。

### 4.2 `MetaNodeExternal.approveTrade`

打开这一段，按注释走：

1. `validOrderSender[orderSender]` 必须为真
2. decode：`Order[]`、`bytes[]` 签名、`uint256[]` 成交 paper
3. 对每张单：EIP-712 哈希、恢复签名（或 EIP-1271）、未过期、paper/credit 异号、未超量成交、taker 不能和 maker 是同一人
4. `Trading._matchOrders` 算出变化
5. 手续费记给 orderSender
6. 返回三列数组给 Perpetual

只有 **已注册的 Perp** 能调 `approveTrade`（`onlyRegisteredPerp`）。用户调 Dealer 这个函数会被拒。

**过关：** 我直接对 Perpetual 调 `trade`，但我不在 validOrderSender 里，失败在哪一层？`approveTrade` 第一句 require。

## 第 5 课：Trading —— 价格和手续费

**目标：** 手验「成交用 Maker 价」。用时约 40 分钟。

打开 `libraries/Trading.sol` 的 `_matchOrders` 和 `_priceMatchCheck`。

规则：

- `orderList[0]` 是 Taker，后面全是 Maker
- Maker 按 signer 地址升序，相同地址允许（同一人多张单合并）
- `matchPaperAmount[0] == sum(后面)`
- 成交 credit 用 Maker 的 `creditAmount/paperAmount`

`_priceMatchCheck`：Taker 买则 Maker 必须卖，且 Maker 价不能差过 Taker 限价（用交叉相乘避免除法）。

手续费：

```
fee = |creditChange| × feeRate
Maker/Taker 的 credit 再减 fee
fee 累加到 orderSenderFee
```

费率从 `info` 位移解析：`>>192` maker，`>>128` taker，`>>64` expiration。

**过关：** Alice 限价 30100 买，Bob 挂 30000 卖。成交 credit 按 30000 还是 30100？按 Maker 的 30000。Alice 作为 Taker 是否仍然安全？因为她最多愿意付 30100，实际更便宜。

## 第 6 课：保证金 —— Funding.sol

**目标：** 分清 deposit 和两步取款。用时约 25 分钟。

打开 `MetaNodeExternal` 的 `deposit`/`requestWithdraw`/`executeWithdraw`，实现在 `libraries/Funding.sol`。

- `deposit`：`transferFrom` USDC，加 `primaryCredit`。不看仓位，不需要 Relayer。
- `requestWithdraw`：记下金额和 `now + withdrawTimeLock`。防止「链下单还在、链上钱先跑」。
- `executeWithdraw`：时间到了才转出，取完要满足保证金（Solid IM / IM，看代码分支）。
- `fastWithdraw`：白名单一步走，教学环境常用来给测试账户。

**过关：** 有持仓时把保证金全部 requestWithdraw，时间锁过后一定能 execute 成功吗？不一定，`isSafe`/`IM` 检查会拦住把账户抽干。

## 第 7 课：风险口径 —— getTotalExposure

**目标：** 能用贯穿例子算净值和是否可清算。用时约 40 分钟。

打开 `libraries/Liquidation.sol` 的 `getTotalExposure`、`_isMMSafe`、`_isIMSafe`。

```
对每个开仓市场：
  (paper, credit) = Perp.balanceOf(trader)
  price = oracle.getMarkPrice()
  仓位价值 += paper × price + credit
  敞口     += |paper × price|
  IM       += 敞口增量 × IMR
  MM       += 敞口增量 × liquidationThreshold

净值 = 仓位价值 + primaryCredit + secondaryCredit
```

贯穿例子：Alice 只开 BTC，deposit 了 5000 USDC，现价 31000：

```
仓位价值 = 1×31000 + (-30000) = 1000
净值     = 1000 + 5000 = 6000
敞口     = 31000
若 IMR=10%，IM = 3100  → 6000 > 3100，可继续开仓
若 MM=5%， MM = 1550  → 6000 > 1550，不会被清算
```

价格跌到什么时候会穿 MM？自己设方程：`paper×P + credit + 保证金 = |paper×P| × 5%`。这就是清算价课要算的东西。

**过关：** 标记价变了，`balanceMap` 变不变？净值变不变？为什么？

## 第 8 课：清算 liquidate

**目标：** 讲清折扣接手和坏账。用时约 35 分钟。

打开 `Perpetual.liquidate` 和 `Liquidation.requestLiquidation`。

流程：

1. 被清算者 MM 不安全
2. Dealer 按标记价加减 `liquidationPriceOff` 算出成交 credit
3. 抽保险费
4. 两边 `_settle`（仓位从被清算者转到清算者）
5. 清算者自己必须仍然 `isSafe`
6. 被清算者 paper==0 则 `handleBadDebt`：若 primaryCredit 为负，保险账户承担

`expectCredit`：清算者提交的最差可接受 credit，防止执行价滑出保护带。

清算是公开函数，不需要 validOrderSender。教学后端的 Liquidator 只是帮你自动叫这个函数。

**过关：** 清算是不是必须把整个仓位一次吃完？接口允许 `requestPaper` 小于仓位。价格保护失败会怎样？整笔 revert，仓位不动。

## 第 9 课：资金费入口与预言机

**目标：** 知道 Keeper 调谁、价格从哪来。用时约 20 分钟。

`Dealer.updateFundingRate(perpList, rateList)` → 每个 Perp `updateFundingRate`。仅 `fundingRateKeeper`。

打开 `oracle/OracleAdaptor.sol` 开头注释：Chainlink 资产/USD 再除 USDC/USD，得到资产/USDC，并做心跳检查。测试里常用 `ConstOracle` / `TestMarkPriceSource` 手写价，方便模拟暴涨暴跌。

清算和 IM/MM **都用标记价，不用订单成交价**，避免被薄盘口操纵。

**过关：** 资金费的正负，在「合约价高于现货」时应该惩罚谁？多头。对应 paper>0 的人 credit 减少，所以 Δ 的符号约定要和 `balanceOf` 公式一起记，读 `ScenarioFundingRateTest` 里断言最清楚。

## 第 10 课：管理员、子账户、把图画完

打开 `MetaNodeOperation.sol` 扫一遍：`setInsurance`、`setFundingRateKeeper`、`setOrderSender`、`setPerpRiskParams`。没有这些，市场无法交易。

`subaccount/`：工厂克隆一个合约当交易账户，EOA 当 owner，便于隔离风险。第一轮可以只知道「signer 可以是合约 + EIP-1271」。

合上代码，填完这条链路：

```
Alice deposit 5000 USDC ──► Dealer.primaryCredit
Alice 签名做多 1@30000 + Bob 签名做空 1@30000
Relayer trade()
  Alice Perp: paper=+1, credit=-30000
  Bob   Perp: paper=-1, credit=+30000
价格到 31000
  Alice 仓位价值 +1000，净值 6000
Keeper 更新 fundingRate
  多空 credit 自动反向移动
Alice 平仓
  realizePnl 进入 primaryCredit
  openPositions 去掉 BTC-PERP
```
